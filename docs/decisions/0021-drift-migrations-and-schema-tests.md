# ADR-0021: Versioned drift schema with migration tests from v1

## Status
Accepted

## Date
2026-09-13

## Context
The cache in ADR-0004 is disposable — in principle a failed migration could drop and rebuild it.
In practice the same database grows non-disposable tables (drafts, an outbox, user preferences)
within a release or two, and by then no migration test harness exists and no historical schema
dumps were ever generated. The historical dumps cannot be recovered after the fact.

## Decision
Set `schemaVersion` from 1 and commit a schema dump per version under `drift_schemas/` via
`drift_dev schema dump`. Every migration gets a test generated by `drift_dev schema generate`
that opens the previous schema, migrates, and asserts the resulting schema matches.

Disposable cache tables may be dropped and recreated in a migration, but that must be written
explicitly in the migration step, never implied by deleting the file.

## Alternatives Considered

### `deleteOnSchemaChange` / wipe the database on any version bump
- Pros: no migrations to write while everything is cache
- Cons: the day a non-disposable table appears, this silently destroys user data
- Rejected: correct today, a data-loss bug on the day the assumption changes

### Start migration tests when the first real migration appears
- Pros: nothing to do now
- Cons: the v1 dump has to exist before v2 to test v1-to-v2; it cannot be produced retroactively
- Rejected

## Consequences
- `make schema` dumps the current schema; CI fails if `schemaVersion` changed without a
  corresponding dump.
- Migration tests run on the native VM, not on web, so web-specific migration behaviour is
  unverified — an accepted gap, noted in the spec's risks.
- Cost is one command per schema change; the dumps are small JSON files.
