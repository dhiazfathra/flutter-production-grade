# ADR-0004: Drift for the offline cache

## Status
Accepted

## Date
2026-09-13

## Context
The products feature is offline-first: it must render cached data immediately, then revalidate
from the network. Targets are iOS, Android, and web. The cache needs queries, pagination, and a
migration story, and the brief favours code generation.

## Decision
Use `drift` with `drift_flutter`. Tables and DAOs are declared in Dart and generated by
`build_runner`. Repositories read from a drift `Stream`, so a cache write pushes straight to the
UI. Web uses drift's `sqlite3.wasm` + worker assets, selected by a conditional import
(`connection/native.dart` / `connection/web.dart`).

## Alternatives Considered
### Key-value JSON cache (`shared_preferences` / `hive_ce`)
- Pros: no wasm assets, trivial setup.
- Cons: no queries, no migrations, no reactive streams over a subset of rows.
- Rejected: it would stop teaching the caching layer past one screen. Still used, separately, for
  small settings values.

### In-memory only
- Pros: nothing to ship.
- Cons: drops offline support, which is in scope.
- Rejected.

## Consequences
- Web builds must vendor `sqlite3.wasm` and `drift_worker.js` under `web/`; a missing asset is a
  runtime failure on web only, so the web integration job is what catches it.
- Schema changes require a schema version bump and a migration step; drift's migration tests are
  part of the suite.
- Unit tests use `NativeDatabase.memory()`, so repository tests exercise real SQL.
